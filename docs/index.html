BankOps-AI

Teach it a legacy banking screen once. Replay it without the model.

An LLM works out how to do a task in a back-office app that has no API. The successful run becomes a typed, versioned capability that an AI agent can call. Every later call replays those steps exactly, with no model involved, and reports whether it succeeded, hit a legitimate business answer, or failed.

How it works

Three stages, one live browser session

1 · Discover

The model finds the way

Claude reads a text view of every frame, with personal data masked, and acts one step at a time. Credentials are filled by the system, so the model never sees them.

runs once · LLM in the loop
2 · Record

The run becomes a capability

Each element the model used gets several ways to find it again, each checked against the live page. Input values become parameters, and each screen change becomes a checkpoint.

typed · versioned · reviewable
3 · Replay

An agent calls it by name

No model decides anything. Each step waits for its checkpoint while watching for known screens like session expiry, notices and error pages, then acts on whichever appears.

every call · no LLM

Finding things on screens with no labels

Look for a control the way an operator would

The target app is deliberately hostile: frames, table layout, no ids, and screens that post back to the same URL. Each recorded step keeps a ranked list of ways to find its control, and replay only acts when exactly one element matches.

roleButton or link by its visible name, e.g. “Inquire”.
anchoredThe box in the table row that reads “Member Number:”.
table_cellRow “SHARE SAVINGS”, column “Balance”, whatever the row order.
textText after a stable label, e.g. “Confirmation #:”.
cssPage position. Last resort, and never used to read data or to commit a change.
Human in the loop

When it gets stuck, a person takes over the same session

  • Only one side controls the session at a time. Automation checks before every action, and the operator's commands carry a token that expires when control is returned.
  • The request carries the capability, the step, the reason, a masked screenshot and the screen text.
  • Everything the operator does is logged. Typed values are never recorded, only that a field changed.
  • On return, replay works out which step the screen matches now and resumes from there. It never repeats an irreversible step.
  • Irreversible actions such as Submit always need approval: from an operator during the run, or from an approved capability plus explicit permission from the caller.
Safety and data handling

Regulated data stays out of logs, files and prompts

  • An allowlist of pages and actions is checked on every step, and again for every network request the browser makes.
  • Member numbers, names, SSNs, dates of birth, phones and addresses are masked in logs, saved results, screenshots, page snapshots and the model's view of the screen.
  • A capability is refused if it contains any of those values. Passwords are looked up at run time and never stored.
  • Approving a capability locks the approval to its exact steps. Any later edit makes it a draft again.
